# ADR-018: クラスタの自己CA・ノード参加・ノード間通信

## ステータス
決定（基本設計書 4.1節の具体化。ADR-013 ④）

## 決定

### 自己CA
- クラスタの最初の1台で「クラスタ初期化」を行うと、そのノードに自己CA（ECDSA P-256、有効期間20年）を作る。
- CAの**秘密鍵はそのノードのローカル秘密情報**（ホスト固有鍵で暗号化、ADR-003）に置く。CA証明書（公開情報）は中央DBにも置く。
- ノード証明書（有効期間5年）はサーバー認証・クライアント認証の両用。SANに`urn:systemagent:node:<ノードID>`を入れ、**相手の確認はホスト名ではなくノードIDで行う**（WSL/NAT環境などでアドレスが重複・変化しても成立するため）。
- CSRの内容（サブジェクト等）は信用せず、CA側が決めたノード名・IDで発行する。
- 失効機能は設けない（ADR-012）。ノードを削除しても発行済み証明書は失効しない。

### ノードの参加
1. 任意のノード（WebUI/CLI）で**参加トークン**（ワンタイム、既定60分）を発行する。トークンには「CAノードの接続先」「CA証明書のSHA-256指紋」「秘密値」が入る。DBには秘密値のハッシュのみ保存する。
2. 新しいノードで`sudo systemagent join <トークン>`（またはWebUIで貼り付け）。新ノードは鍵ペアを自分で生成し、秘密鍵は外に出さない。
3. 新ノードはCA証明書を取得して**トークンの指紋と照合**し、以降はそのCAで署名されたサーバー証明書でなければ接続しない（参加前でも中間者攻撃を防ぐ）。
4. CAノードはトークンを検証・消費し、CSRに署名してノードをDBに登録する。

### ノード間通信
- 各ノードはWebUI/API用のポートとは別に、**ノード間通信用のTLSポート**（`Cluster:Port`、既定5443）で待ち受ける。クライアント証明書はクラスタCAで署名されたノード証明書のみ受け付ける。
- 認証はDBに依存しない（CA証明書・ノード証明書はローカル秘密情報にある）。
- 他ノードへの接続時は、接続先の証明書のノードIDが**接続しようとしたノードのID**と一致しなければ拒否する（接続先ごとにクライアントを分けてTLS検証に組み込む）。

### 他ノードの操作（転送）
- `/api/nodes/{id}/proxy/api/...` を対象ノードの `/api/...` にmTLSで転送する汎用の仕組みとした。これにより既存・今後の全機能を機能ごとの実装なしに他ノードで使える。
- 転送先では操作者を`<ユーザー>@<転送元ノード>`として監査ログに残す（`X-SystemAgent-Actor`ヘッダ。ノード証明書で認証された接続からのみ受け付ける）。
- WebUIは画面上部の「操作対象ノード」、CLIは`--node <名前|ID>`で切り替える。
- 転送のループを避けるため、転送先で再度の転送はしない。

## 設定
| キー | 既定 | 内容 |
|---|---|---|
| `Cluster:Port` | 5443 | ノード間通信の待ち受けポート（0で無効） |
| `Cluster:NodeName` | ホスト名 | ノード名（クラスタ内で一意） |
| `Cluster:AdvertiseAddress` | デフォルトゲートウェイ側のIPv4 | 他ノードからの接続先 |

## 既知の制約・今後
- CAノードが停止している間は新しいノードを参加させられない（既存ノード間の通信には影響しない）。CA鍵のバックアップ/移設は別途検討。
- 証明書の更新（期限切れ前の再発行）は未実装。有効期限はWebUIのノード一覧・`systemagent node list`で確認できる。
- 検証: WSL上の3ノード（AlmaLinux 9 / Ubuntu 24.04 / Debian 13）で、初期化・参加・トークン再利用の拒否・他ノードのコンテナ/NTP操作・監査ログの操作者記録・クライアント証明書なし接続の拒否を確認。
