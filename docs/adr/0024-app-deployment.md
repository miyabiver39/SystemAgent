# ADR-024: 自社アプリ（コンテナ）のイメージ更新・デプロイ

## ステータス
暫定決定（基本設計書 2.1節「デプロイ機能」。確認事項は [QA-0006](../qa/questions/0006-deployment.md)）

## 決定
- デプロイの単位は**アプリ = 1コンテナ**。定義はコンテナ名・タグなしのイメージ・ポート公開・環境変数・ボリューム・Pod（Podmanのみ）・再起動ポリシー・取得方針・動作確認の秒数。タグはデプロイ時に指定する。Docker Compose は対象外（設計書 1章）。
- 定義は**ノードごと**に、ローカルの暗号化シークレット（`deploy.apps`）へ保存する。
  - 環境変数にDBパスワード等の秘密情報を含み得るため暗号化する。名前に PASS / SECRET / TOKEN / KEY / CREDENTIAL を含む環境変数の値はAPI・画面では `********` で返し、伏せ字のまま保存し直すと保存済みの値を引き継ぐ。
  - 中央DBが停止していても（緊急ログインで）デプロイ・ロールバックできる。
  - 他ノードへのデプロイは転送（ADR-018）で行う。全ノード一括デプロイは行わない。
- 手順
  1. イメージを取得する（取得方針 Missing: ローカルに無い時だけ / Always: 毎回）。レジストリの認証情報があれば先にログインする（ADR-023）。**取得に失敗した場合は既存コンテナに一切触れない**。
  2. 既存コンテナを停止し `<名前>-previous` に改名して退避する。
  3. 新しいコンテナを起動する（ラベル `io.systemagent.deployment=<名前>` を付ける）。
  4. 指定秒数（既定10秒）待ち、**動作中かつ再起動回数が0**なら成功。再起動ポリシーで再起動を繰り返しているコンテナは確認した瞬間に動作中に見えるため、再起動回数も確認する。
  5. 成功したら退避したコンテナを削除する（イメージはロールバック用に残す）。失敗したら新しいコンテナを削除し、退避したコンテナを元の名前に戻して起動する（この復旧は要求の取り消しでは中断しない）。
- ロールバックは「1つ前にデプロイしていたタグ」を同じ手順でデプロイする。
- 同じアプリへの同時操作は 409。デプロイの失敗（元に戻した）は 422。履歴はアプリごとに直近30件をローカルに保存し、監査ログにも残す。
- 可変長の引数（ポート・環境変数・ボリューム）はコマンドテンプレートのリストプレースホルダ `{*name}` で渡す（引数を値の数だけ繰り返す。0件なら省略）。値は `--publish=` のように同じ引数に連結し、オプションとして解釈されないようにする。各値は形式を検証する。
- Podman で `--restart=always` のコンテナをOS再起動後にも起動するには `podman-restart.service` の有効化が必要。サービス管理（ADR-021）の管理対象に追加した。

## 検証
- 単体テスト（`DeployTests`）: 更新・起動失敗・再起動ループ・起動コマンド失敗・取得失敗時の復旧、ロールバック、秘密情報の伏せ字、入力検証、テンプレートの展開。
- WSL（sa-alma9 / Podman 5.8、認証付き registry:2）で、自動ログイン取得 → 更新 → 異常終了するイメージの自動復旧 → 存在しないタグ（既存コンテナは停止しない）→ ロールバックを確認した。Docker 用テンプレートはコマンド生成のみ確認。
