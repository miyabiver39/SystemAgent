# 0006: デプロイ機能の暫定方針の確認 への回答

- 回答日: (未記入)

質問は[../questions/0006-deployment.md](../questions/0006-deployment.md)を参照。暫定方針のままで良い項目は「OK」だけで構いません。

## A1（Q1: デプロイの単位）
基本的にはOK。しかし、複数コンテナで1つのアプリを構成することもあるため、Pod単位でのデプロイもサポートする方が良い。
コンテナの起動順序・依存関係もある。定義しておくのがよい。
毎回ヒトが手動で作成するのは大変なので、プリセットのPod定義を用意しておき、デプロイ時に選択できるようにするのが良い。プリセットの登録ができると良い。また、Seederによって開発者が事前に定義できるのがよい。

## A2（Q2: 保存先と複数ノード）
同じアプリを複数ノードへ一括デプロイする必要はある。中央DBが止まっていても、デプロイ・ロールバックできるのはありがたい。。。実現可能性が不安だが、エアギャップで構築して導入することもあると考えられるため。

## A3（Q3: 成功判定）
ヘルスチェックも必要。HEALTHCHECKを使う方法もあるが、アプリの仕様によってはヘルスチェックができない場合もあるので、HTTPのヘルスチェックもサポートする方が良い。

## A4（Q4: 停止時間）
完全無停止ができるとよいが、仕組みが複雑にならないか？実現できるのであれば、頼みたい。


## A5（Q5: Jenkins）
自動デプロイは不要。このアプリはお客様先に導入することはメインであるため、開発環境で自動デプロイする必要はない。
