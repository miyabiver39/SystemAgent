# 0003: 認証まわりの運用方針

- ステータス: 未回答
- 起票日: 2026-09-26
- 関連: 基本設計書 5.2節・6章、ADR-003

認証基盤（通常JWT + ローカル緊急認証）を実装しています。以下は**暫定方針で実装を進めています**。問題があれば回答いただければ修正します。

## Q1. ローカル緊急認証は「DB停止中のみ」有効にすべきか
設計書5.2節のフロー図は「DB未起動 → 緊急認証のみ有効」「DB起動済み → 通常JWT認証」と読めますが、DB稼働中に緊急認証を禁止するかは明記されていません。

- **暫定方針（実装済み）**: 緊急認証は**常に利用可能**（いわゆるブレークグラス）。DB稼働中に使われた場合は監査ログに記録する。
- 代替案: DB接続可能な間は緊急ログインを拒否する（DB障害時にしか使えないため安全側だが、DBユーザーのパスワードを全員忘れた場合などに詰む）。

## Q2. 初期管理者パスワードの受け渡し方法
インストール直後はDBユーザーが存在しないため、最初は緊急認証でログインしてDBユーザーを作成する流れになります。

- **暫定方針（実装済み）**: 初回起動時（将来はRPM/DEBの`%post`）に緊急ユーザー`admin`をランダムパスワードで生成し、秘密情報ディレクトリ内の`initial-admin-password`ファイル（パーミッション600）に書き出す。ログには**パスワードではなくファイルパスのみ**を出す（Jenkinsの初期パスワードと同じ方式）。管理者はログイン後にパスワードを変更する。
- 代替案: インストール時に対話的にパスワードを入力させる（ただしRPM/DEBのインストールは非対話が原則）。

## Q3. 権限（ロール）の区別
非機能要件で同時利用2〜3人とあるため、**暫定方針では権限の区別なし**（ログインできれば全操作可能）としています。閲覧専用ユーザー等のロールが必要であれば教えてください。

## Q4. トークンの有効期限
**暫定方針**: アクセストークンの有効期限は8時間（設定で変更可能）、リフレッシュトークンなし（期限切れ時は再ログイン）。業務時間中に再ログインを求めない想定です。
