# 0006: デプロイ機能の暫定方針の確認

- ステータス: 未回答
- 起票日: 2026-09-28
- 関連: 基本設計書 2.1節「デプロイ機能」、[ADR-024](../../adr/0024-app-deployment.md)

デプロイ機能（自社アプリのイメージ更新）を**暫定方針で実装済み**です。運用に合わない点があれば教えてください。問題なければ「OK」だけで構いません。

## Q1. デプロイの単位
- **暫定: アプリ = 1コンテナ。** 複数コンテナで1つのアプリを構成する場合は、Pod（Podman）を別途作成し、各コンテナをPodに参加させて個別にデプロイする形です。
- 複数コンテナをまとめて1回で更新する（順序・依存関係あり）必要はありますか？

## Q2. 定義の保存先と複数ノード
- **暫定: 定義はノードごと（暗号化してローカル保存）。** 中央DBが止まっていてもデプロイ・ロールバックできることを優先しました。
- 同じアプリを複数ノードへ一括デプロイ（例: 片方ずつ順番に更新する）する必要はありますか？ 必要なら「定義を中央DBで共有し、ノードを選んで順次デプロイ」を追加します。

## Q3. 成功判定
- **暫定: 起動後N秒（既定10秒）動作し続け、再起動していなければ成功。** 失敗時は自動で元のコンテナに戻します。
- HTTPのヘルスチェック（例: `http://localhost:8080/health` が200を返す）まで必要ですか？ イメージの HEALTHCHECK を使う方法もあります。

## Q4. 切り替え時の停止時間
- **暫定: 旧コンテナを停止 → 新コンテナを起動（停止時間は数秒〜起動時間分）。** 同じポートを使うため同時起動はできません。
- 無停止が必要なアプリはありますか？（その場合は Keepalived のVIPを使ってノード単位で切り替える運用を想定しています）

## Q5. Jenkins からの自動デプロイ
- **暫定: 未対応（手動でWebUI/CLIから実行）。** QA-0001 で Jenkins は後回しとなっているため。
- 必要になった時点で、Jenkins から呼べる専用トークン（有効期限なし・デプロイのみ可）の仕組みを追加する想定です。
